# Gate 0 实测结论（Windows 采集层）

日期：2026-09-22　机器：Windows 11 build 26200　微信：**4.1.13.65**（`Weixin.exe`，Qt 5.15.14 重写版）
探针：`tools/win-spike/probe_capture.py`、`tools/win-spike/probe_area.py`

结论先行：**采集这条路走通了**。WGC 能拿到真实像素、**窗口被完全遮挡也能拿到**、消息区能用像素锚点稳定定位。
唯一硬限制是最小化时零帧，我们选择"提示用户"而不是"强制还原窗口"。

---

## R1 采集通道（`probe_capture.py`）

### 窗口定位

主窗口：`hwnd=4718974`，类名 `Qt51514QWindowIcon`，标题 `微信`，客户区 `1920x1032`（`GetWindowRect` 是 `1936x1048`，差 16px 边框）。

踩过的两个坑：

1. 微信有多个类名命中的窗口，其中 `hwnd=42469868` 是 `176x199` 的**隐藏辅助窗口**（标题 `Weixin`，`vis=0`）。按"面积最大"选会选错它。
2. 主窗口**最小化时 `GetWindowRect` 塌缩成 `160x28`**，按面积评分同样会输给辅助窗口。

修法：先排除 `IsWindowVisible=0` 的窗口，再按 `GetWindowPlacement[4]`（`rcNormalPosition`，还原尺寸）评分。
实测主窗口还原尺寸 `1344x668` / `986x817`（用户手工调整过），辅助窗口 `176x199`，判据稳定。

### 三种窗口状态的取帧结果

| 状态 | 结果 |
|---|---|
| 前台可见 | 出帧。`(1032, 1920, 4)` `mean=37.95` `std=26.03` `colors=24526` `近黑=0.001` → **真实像素** |
| **被其它窗口完全遮挡** | **仍然出帧**。遮挡色占比 `0.000`，`mean=37.37` `std=24.87` `colors=24368`，与基线几乎一致 |
| 最小化 | **零帧**（3 秒内 0 帧，无报错、无异常）。`WindowsCapture.start()` 会永久阻塞，必须用 `start_free_threaded()` + 自己计时停止 |

遮挡测试的做法：自己开一个 `1936x1048` 的纯色 tkinter 窗口（`#FF00AA`）盖住微信，再采一次，然后统计帧里遮挡色的占比。
`0.000` 说明 WGC 拿的是**窗口自己的合成表面**而不是屏幕像素——这是它相对 `BitBlt`/`ImageGrab` 的决定性优势，也意味着副驾在微信被压在其他窗口后面时照样能工作。

### 关键实现细节

- `draw_border=False` 被接受、无报错。Win11 上未观察到采集边框干扰（Win10 上无法关闭，是已知代价）。
- WGC 只在内容变化时送帧（8 秒 8 帧）。所以**"最后一帧到达"不等于"已经静默"**——静默判定必须由独立定时器做，否则内容稳定后不再送帧、稳定帧永远发不出去。这条踩过：初版靠帧到达判定，实际一直在用 max_wait 兜底。
- 采集启动后的**第一帧是未渲染空帧**，此时"右半区众数色"被算成黑色，把定位拖成一整屏 `(0,32,1920,1032)` 并缓存下来。修法：帧健康检查（近黑占比 >0.90 或 `std<1.5` 直接丢）+ 定位合理性校验（左边界>0、下边界<窗高、尺寸>200px），无效定位不缓存。

## R2 消息区定位（`probe_area.py` → 已沉淀为 `desktop/area.py`）

实测锚点（深色模式，客户区 1920x1032）：

| 锚点 | 实测值 | 判据 |
|---|---|---|
| 聊天区底色 | `(30,30,31)` | 右半区出现最多的颜色（占 76%） |
| 左边界 | **x=289** | 逐列算底色占比，跃升到 >0.50 的第一列（此处 0.964） |
| 上边界 | **y=32** | 从 y=0 起第一条"整行不再同色"的行 |
| 下边界 | **y=815** | 消息区内第一条"整行同色且不是底色"的横向分隔线 |

**消息区矩形 = (289, 32) - (1920, 815)，1631x783，占全图 64.5%。** 调试图核对通过（`out/area_debug.png`）：左让开会话列表、上让开标题条、下**正好切在输入区上沿**，最后一条消息完整在框内。

最大的坑：**输入区的底色和消息区完全相同（都是 `(30,30,31)`）**，唯一能区分的是 y=815 那条分隔线（整行同色 `(39,39,40)`，占 0.979）。
所以分隔线判据必须容忍 0.98 以下的占比——阈值卡到 0.985 会跳过它，最后把窗口底边 `1028` 当成下边界。这个 bug 真踩过，已写进 `desktop/area.py` 的注释。

三个背景带（供以后对照）：最左图标条 `(45,45,46)`、会话列表 `(47,47,48)`、聊天区 `(30,30,31)`。

## R3 端到端预算（真实调用）

感知 = DeepSeek 视觉（`deepseek-flash`，思考型模型）；判断/排序 = Jev（`api.typesafe.ai` 直连，`jev-latest` → `jev-1.13.0`）。

| 环节 | 实测耗时（多次） | token |
|---|---|---|
| 感知 | 4.39 / 4.79 / 5.72 / 5.87 / 5.94 / 6.59 / 7.07 / **15.46** s | 1347 输入 / 732~918 输出 |
| 判断 | 1.01 / 1.21 / 1.52 / 1.69 s | 2437 / 272 |
| 起草 | 2.17 / 3.94 / 5.17 / 7.02 s | 308 / 309 |
| 排序 | 0.92 / 0.96 / 0.99 / 1.13 s | — |
| **合计** | **8.7 / 13.7 / 13.9 / 16.5 s** | |

### 两个反直觉的实测结论

1. **裁小图不能降延迟。** 把消息区从 783px 裁到底部 420px，耗时反而从 4.79s 涨到 6.41s：输入 token 从 1347 降到 987，**输出（推理）token 从 732 涨到 918**。耗时由思考型模型的推理长度主导，不是图像大小。而且裁掉标题会丢会话键、字符读错变多（"某为"→"巽为"）。**生产路径送完整消息区。**
2. **判断比感知快得多**（1.0~1.7s vs 4.4~15.5s）。所以两段式渲染是对的：危险等级和意图能在感知结束后 1 秒内出来，候选再慢补。

## 会话隔离（参考项目的真实缺陷，我们已补）

视觉模型对**群名的读取不稳定**——同一次会话实测读出过：

```
'硅基妙妙屋 (50)'   →   '硅基炒饭屋 (50)'   →   'jev-chat-JARVIS 📌 群 (212)'
'jev-chat-JARVIS'   →   'jev-chat-JARVIS 1 群 (212)'   →   'jev-chat-JARVIS 群 (212)'
```

`炒饭`/`妙妙` 是同一次误读。所以会话键**不能用标题精确匹配**——每次误读都会被当成"切了会话"、反复清空状态。
`desktop/engine.py` 用归一化 + 子串 + `SequenceMatcher ≥ 0.60` 兜住，实测正确：真正的会话切换（`硅基妙妙屋` ↔ `jev-chat-JARVIS 群`）被识别并清空状态，误读没有被误判。

参考项目 `rezoch340/jev-chat-JARVIS-windows` 没有这层：它只有一个全局 `history` 队列、去重状态跨暂停保留、OCR 也不读会话标题，
所以切换会话后新消息会追加进同一个缓冲，state 里混两个会话的内容。

## 未覆盖 / 风险

- **感知有间歇性空返回**：8 次里 1 次，思考型模型烧完 4000 个 `max_tokens` 后正文为空。下一轮自愈，但该次分析丢失。
- **群聊档案未校准。** 当前打开的会话是群聊，走的是 `group` 档案，`questions.json` 里标着 `calibrated: false`，结论仅供参考。**一对一（已校准）路径在有单聊窗口前没跑过。**
- **延迟 8.7~16.5s，不适合作实时副驾。** 瓶颈是感知（思考型模型把 700~900 token 花在推理上）。换非思考型视觉模型或降低推理预算是最直接的优化，但需要另配 provider。
- **最小化时零帧**，App 只提示不还原（不擅自动用户窗口）。
- **窗口重建/尺寸过渡会杀掉 WGC 会话**（实测遇到一次选中过渡态窗口 `3840x1080`、会话立刻关闭）。已加自动重挂 + 1.5s 冷却，但只覆盖到"下一次空闲轮询"。
- **只在微信 4.1.13.65 + 深色模式 + 默认主题下测过。** 浅色模式、自定义聊天背景、窗口缩放、多显示器下的定位都没验；颜色类假设在浅色下未复核。
- 微信随时会被最小化（本次测试期间反复发生），真实可用性依赖用户保持窗口可见。
