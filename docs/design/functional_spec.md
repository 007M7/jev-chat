# Jev 功能设计规格（iOS / Windows 共享）

版本：v1　日期：2026-09-22　用途：**iOS 与 Windows 两个实现共用同一份功能规格**，避免各写一套后语义漂移。

这份文档只定义**功能与数据契约**，不定义像素。界面尺寸、控件、平台特有的交互各自实现，但下列语义必须一致：

- 会话与发言人的数据结构
- 三类设置的字段与生效范围（身份 / 情绪 / 回复风格）
- 判断结果的字段与排序规则
- 哪些能力在哪个平台做不到（先说清楚，免得实现方互相等）

---

## 一、平台边界（先看这张表，避免无效对齐）

| 能力 | Windows | iOS | 说明 |
|---|---|---|---|
| 采集方式 | WGC 截自己的微信窗口 | ScreenCaptureKit 全屏采集 | iOS 拿不到单窗口，会带上键盘/通知/灵动岛 |
| 悬浮窗 | ✅ 半透明置顶面板 | ❌ **系统不提供** | iOS 走通知横幅 + 灵动岛 |
| 「填入」输入框 | ✅ 可写进输入框 | ❌ **做不到** | iOS 只能写剪贴板，用户长按粘贴 |
| 一键复制 | ✅ | ✅ | 两端都有 |
| 主动发送 | ❌ 两端都不做 | ❌ | 红线：发送永远由人手动点 |
| 记忆档案存哪 | 本机文件 | 本机沙盒 + Keychain | 都不上云（除判断所需的对话内容） |

**iOS「填入」是做不到的**，不是没做——App 无法往别的 App 的输入框写文本。所以 iOS 的候选按钮叫「复制」，Windows 的叫「填入」，这是平台差异不是功能缺失。

## 二、核心数据模型

### 2.1 会话（Session）

两端共用的会话标识。**标题会被视觉模型读错**（实测同一张图两次读出「读书会(50)」「读书舍(50)」），所以要用归一化 + 相似度做键，不能逐字比。

```json
{
  "session_key": "归一化后的键，用于本地状态索引",
  "title": "原始标题，如 jev-chat-JARVIS 1 群 (214)",
  "title_normalized": "去空格/全半角统一/去表情后的标题",
  "app": "wechat",
  "is_group": true,
  "members": ["Nox.", "Aster", "林伟"],
  "distinct_speakers": 3,
  "created_at": "2026-09-22T00:00:00Z",
  "last_active_at": "..."
}
```

**要点**
- `is_group` 由感知层给（视觉模型直接判断），不靠标题里有没有「群」字
- `distinct_speakers` 是**对方阵营**的去重发言人数。=1 时说明实质是一对一会话，此时可以退回一对一题目档案
- `session_key` 用于会话隔离：切换会话必须清空历史与去重状态（参考实现踩过：不隔离会让 state 混两个会话的内容）

### 2.2 消息（Message）—— 群聊区分发言人的基础

```json
{
  "side": "me | other",
  "sender": "Aster",        // 群聊里必填；一对一为 null
  "kind": "text | sticker | image | voice | quote | payment | system",
  "text": "我改成 OpenAI 的",
  "quote_text": "被引用的原文（kind=quote 时）",
  "description": "表情包/图片的一句话描述（kind=sticker|image 时）",
  "sent_at": "可选，截图里能读出时间才填"
}
```

**硬要求**
1. **群聊里 `sender` 必须填**。把多个发言人压成一个 `other` 是本项目已修过的真实缺陷：判断层会以为所有话都是同一个人说的，于是无法判断"这个问题别人已经回答过了"。
2. **非文本内容必须转成可读描述**（`[图片：一只黑猫躺着]`）。这是本地 OCR 方案结构上拿不到、而决定了"对方只发一个表情包时能不能触发分析"的部分。
3. **折行消息合并成一条**，不要按行拆。
4. 界面浮层内容（悬浮窗/通知/输入框草稿/时间戳/系统提示）**不得**进入 `messages`。

### 2.3 身份设置（IdentityConfig）—— 按会话独立配置

这是"我是谁 / 对方是谁"的显式配置。**它优先于任何泛化假设**：判断层原本要猜"对方是不是在测试我在不在乎"，有了身份设置就不用猜。

```json
{
  "session_key": "...",
  "me": {
    "display_name": "我",
    "role": "项目作者 / 群主",           // 我在这个会话里的角色
    "tone": "简洁、技术向、不用敬语"       // 我在这儿的说话风格
  },
  "counterpart": {                       // 一对一：对方；群聊：留空
    "display_name": "Aster",
    "relationship": "同事 / 一起做项目的",
    "tone": "直接、爱吐槽",
    "boundaries": ["不要在群里提钱"]       // 忌讳与边界
  },
  "group": {                             // 群聊专用
    "purpose": "项目交流群，讨论实现与需求",
    "members": [
      {"name": "Aster", "role": "协作者", "tone": "直接、爱吐槽"},
      {"name": "Nox.", "role": "用户/观察者", "tone": "简短"}
    ],
    "norms": ["讨论技术细节可以公开", "拉人靠挂二维码，不手动拉"],
    "audience_size": 214                  // 影响措辞：群里 200 人 vs 3 人完全不同
  },
  "relationship_prompt": "最终送进判断层的自然语言描述（由上面的字段拼出，也可手改）"
}
```

**生效范围**：按 `session_key` 独立。同一群里的不同人可以有不同角色，但 `tone`/`boundaries` 是会话级的（当前实现如此，逐人覆盖留作后续）。

**与记忆档案的关系**：身份设置是**人工填的权威值**；记忆档案是**从对话里蒸馏出来的候选**。冲突时以人工值为准，蒸馏结果只在人工没填的字段上生效。这一条必须两端一致，否则会出现"我以为改对了但模型还在用记忆里的旧身份"。

### 2.4 回复风格（ReplyStyle）—— 「情绪设置」里我方的部分

截图里的 `高情商话术` / `贴吧老哥 v1.0` / `不用`，就是这一层。它是**候选回复的生成维度**，不是 UI 装饰。

```json
{
  "style_id": "tactful",
  "name": "高情商话术",
  "enabled": true,
  "order": 1,
  "applies_to": {"session_keys": ["..."], "is_group": true},
  "instruction": "措辞得体，先承接对方情绪再给方案，不用网络梗，不油腻。",
  "example": "收到，我这就按 OpenAI 来改，今天给你。",
  "max_chars": 40,
  "candidates_per_style": 2
}
```

**内置风格（建议两端一致）**

| style_id | 名称 | instruction 要点 | 适用 |
|---|---|---|---|
| `tactful` | 高情商话术 | 先承接情绪，再给具体方案；不用梗 | 通用 |
| `concise` | 简短直接 | 一句话给结论，不解释 | 忙/技术沟通 |
| `forum_bro` | 贴吧老哥 | 网络用语、自嘲、玩梗，轻松 | 熟人群、闲聊 |
| `apologetic` | 低姿态 | 先认错，不辩解，给补救 | 冲突场景 |
| `defer` | 先确认再回 | 说明需要核对什么，给时间点 | 事实不确定 |
| `no_reply` | **不用** | 不回复 | 话题已收尾/没问我 |

**要点**
- `no_reply` **必须是一个风格项**，而不是"没有候选"的空状态。截图里把它列成第三个折叠组是对的：它让"不回"变成可主动选择的建议，而不是无声的失败。
- 每个风格**独立排序**（截图里 `高情商话术 #1 17%`、`贴吧老哥 #1 53%` 是两套组内排序），跨风格不排名。理由：风格是用户的偏好维度，硬排名会把"更适合的风格"混进"更合适的措辞"里。
- 当前实现里 Jev 排序是跨候选统一排的。要支持分组排序，需要**按风格分组各调一次排序题**（成本 ×风格数），或者一次排序请求里带 `style_id` 让模型分组输出。**这条建议两端一起定**（见第八节）。

### 2.5 对方情绪与风险（RiskState）—— 「情绪设置」里对方的部分

截图里的 `● 留神 4/9` 就是它。分两层：**数值**给机器用，**中文标签**给人看。

```json
{
  "danger_level": 4.0,
  "danger_label": "留神",
  "danger_hint": "轻松回应 · 可以互动 · 不用当真",
  "intent": "casual_chat",
  "intent_label": "闲聊",
  "intent_confidence": 0.35,
  "tension_resolved": false,
  "should_reply_now": false
}
```

**危险等级的中文标签映射（建议两端一致）**

| 等级 | 标签 | 配色 | hint 要点 |
|---|---|---|---|
| 0–1 | 安全 | 绿 | 正常聊，随便回 |
| 2–3 | 留意 | 浅绿/黄 | 有轻微提醒，别敷衍 |
| 4–5 | 留神 | 橙 | 轻松回应、可以互动、别当真/别升级 |
| 6–7 | 危险 | 深橙 | 要正面回应，别玩梗 |
| 8–9 | 紧急 | 红 | 先止损：道歉/承诺/少说 |

**意图的中文标签**：`confirm_you_care` 在乎确认 / `vent_anger` 情绪发泄 / `request_action` 要你办事 / `seek_explanation` 要个解释 / `casual_chat` 闲聊 / `close_topic` 话题收尾。

**低置信度必须有显示策略**（截图里 `意图识别率 35%`）。实测同一批题目里 `best_action` 的把握度只有 14%~30%。建议：
- 置信度 < 50% 时，标签旁显式标注置信度，并**降低提示强度**（不要用"危险"这种确定语气）
- 置信度 < 40% 时，界面上给一句"判断不确定，建议自己看一眼"

### 2.6 判断结果（Judgment）—— 两端共用的返回体

```json
{
  "session_key": "...",
  "profile": "group",              // one_on_one | group
  "calibrated": false,             // 该档案是否已用标注集校准
  "speaker": {"name": "Aster", "source": "perception"},   // 最新消息的发言人
  "context_line": "还是走了 openrouter 的协议",              // 同人上一条，给"上文"用
  "risk": { ...见 2.5... },
  "action_advice": "轻松回应 · 可以互动 · 不用当真",
  "candidates": [
    {"style_id": "tactful", "rank": 1, "score": 0.17, "text": "收到，我这就按 OpenAI 来改，今天给你。"},
    {"style_id": "tactful", "rank": 2, "score": 0.04, "text": "懂了，全体切 OpenAI，我马上换，明早准到。"},
    {"style_id": "forum_bro", "rank": 1, "score": 0.53, "text": "好家伙搁这偷偷换 OpenAI，我先绷为敬了哥。"}
  ],
  "consistency_warnings": ["不需要我回复时不该建议「直接作答」"],
  "usage": {"perception_s": 3.4, "judge_s": 1.0, "draft_s": 5.8, "tokens_in": 3600, "tokens_out": 1800}
}
```

**`calibrated: false` 必须在界面上可见**。群聊档案目前未经标注集校准，`consistency_warnings` 也非空——把"我知道这里还不准"如实显示出来，比假装自信安全。

## 三、群聊区分发言人：端到端规格

这是本轮的核心。四层都要做到，缺一层就会退化。

### 第一层 · 感知：必须拿到每条的发言人

感知模型返回的每条消息都要有 `sender`。提示词里要明确：
> 群聊里同一侧有多个发言人，这些都属于 other，同时在 sender 里写明昵称；不要用"左右"作为唯一依据。

**已知问题：昵称会被读错。** 实测同一昵称读出过三种结果（其中一种完全无关）。所以要有**别名归并**：

```json
{
  "aliases": {
    "Aster": ["Aster", "Astero", "aster"],
    "Nox.": ["Nox.", "Nox", "Lull."]
  },
  "rule": "归一化 + 相似度 ≥ 0.6 视为同一人；低于阈值时新建发言人并在界面上标注「疑似新成员」"
}
```

**不要用模型给的昵称当主键**，用归一化后的键 + 人工确认。

### 第二层 · 状态：把发言人送进判断层

```
chat.messages[]: {"from": "me|other", "text": "...", "sender": "Aster"}
chat.senders: ["Nox.", "Aster"]
chat.distinct_speakers: 3
```

判断层的题目指令里必须写明"每条消息带 sender、不要假设最新发言人与之前是同一个人"。**只把 sender 塞进 state 而不改指令，模型不会用**——这条已在 iOS 侧验证。

### 第三层 · 判断：需要发言人的题目

| 题目 | 为什么要发言人 |
|---|---|
| 是否在问我 | 群聊里多数消息不是对我说的；要区分"对我说"和"对别人说" |
| 需要我回复吗 | "别人已经回答了"只有知道谁说了什么才能判断 |
| 最佳动作 | 别人已答时该 `no_reply`/`acknowledge_brief`，而不是重复作答 |
| 对方想从我这里要什么 | "想要资源"vs"想要**我**提供资源"是两件事（这条区分错过一次，见附注） |

**附注（真实踩坑）**：一致性检查曾把「对方想要资源」和「对方想要我提供资源」混为一谈，产生假阳性。规则必须带 `asked_to_me` 前提：群里有人号召大家拉朋友时，`need_from_me = nothing` 是正确的。

### 第四层 · 界面：把发言人显示出来

截图里的 `来自 Aster · 上文: 还是走了 openrouter 的协议` 就是这一层，必须保留：
- **发言人名**：让人一眼知道在回谁
- **上文**：同一个人此前最近的一条，避免误把别人的话当成他的话
- 群聊里候选措辞要考虑**受众规模**（214 人的群里说话和一对一完全不同）

## 四、设置项汇总（两端一致）

| 设置 | 粒度 | 作用 | 默认 |
|---|---|---|---|
| 身份：我是谁/我在这儿的角色 | 会话 | 影响语气与"该不该出头" | 空 |
| 身份：对方是谁/关系 | 会话 | **替代"关系前提靠猜"** | 空（必须填才能发挥准确度优势） |
| 身份：群定位/成员角色/群规/人数 | 群会话 | 影响措辞与公开性判断 | 空 |
| 边界：忌讳话题 | 会话 | 生成候选时规避 | 空 |
| 风格：启用哪些回复风格 | 全局 + 按会话覆盖 | 决定候选的生成维度 | 高情商话术 + 不用 |
| 风格：每个风格几个候选 | 全局 | 成本与信息量平衡 | 2 |
| 风险：危险等级文案 | 全局 | 标签/配色/hint | 见 2.5 表 |
| 判断：题目档案 | 自动（is_group） | 一对一 / 群聊 | 自动 |
| 记忆：档案开关 + 蒸馏开关 | 会话 | 是否读写长期记忆 | 读开、写关（写要花钱） |

**「情绪设置」的完整含义（澄清）**：它包含两部分，不要混为一谈——
1. **对方的情绪/风险**（2.5）：由判断层算出，用户只读
2. **我方的回复风格**（2.4）：用户可配，作为候选项的生成维度

## 五、记忆档案（与身份设置配合）

已实现的设计要点（细节见 `docs/ios/product_memory.md`）：

| 规矩 | 说明 |
|---|---|
| 必须带出处 | 每条记忆存消息原文片段，没出处的不入库 |
| 只存可核对的事实 | 存「他说'你不用手动拉人'」，不存「他很在意拉人效率」 |
| 结构化字段 | `kind` / `key` / `about` / `expires` |
| 有生命周期 | `commitment` 类必须给过期日 |
| 按人归档 | `about` 标明这条关于谁——群聊里这是必须的 |
| 冲突时人工优先 | 与身份设置冲突时以人工填的为准 |

五类：`identity` / `fact` / `commitment` / `preference` / `boundary`。

## 六、界面功能规格（对齐截图）

面板从上到下七个区块。**每一块都有存在的理由，不是排版喜好**：

| 区块 | 内容 | 为什么必须有 |
|---|---|---|
| 1 会话标题 | 绿色高亮标题 + 群人数 | 会话隔离的可见证据；也提醒"这是 214 人的群" |
| 2 分析状态 | 分析完成 / 读屏中 / 判断中 | 两段式渲染（判断先出、候选后补），不让人干等 |
| 3 最新消息 + 发言人 + 上文 | `我改成 OpenAI 的` / `来自 Aster · 上文: ...` | 发言归属的核心展示 |
| 4 意图 + 置信度 | `闲聊` / `意图识别率 35%` | 低置信度要可见 |
| 5 风险等级 | `● 留神 4/9` + hint 短语 | 数值 + 中文标签 + 可执行建议，三层缺一不可 |
| 6 候选回复（按风格分组） | 风格折叠组 → 组内 `#1 · 53%` + 复制/填入 | 风格是用户偏好维度，不与措辞合适度混排 |
| 7 折叠的「不用」 | 不回复作为一个可选项 | 让"不回"成为建议，而不是沉默的失败 |

**平台差异**：`填入` 按钮 Windows 有、iOS 没有（改为"复制"，用户长按粘贴）。其余一致。

## 六之二、记录层的三段结构（两端都应照此拆分）

用户实测反馈：「**记录内容分成分析记录和群聊记录**；会话档案直接分成群组；人物可以做一个可查看检索的联系人目录」。
这不是排版偏好——**混在一起会让"感知只读了一条消息"变成观感事实**：
记录页原本每条只展示「最新消息 + 一行上文」，看起来就像模型只读了一句，
而实际上感知送的是整屏、判断用的是最近 10 条。分离之后，累积的对话流自己会说话。

| 层 | 内容 | 归属 | 生命周期 |
|---|---|---|---|
| **会话记录**（群聊记录 / 聊天记录） | 逐条对话原文，带 `side` 与 `sender` | 按会话 | **跨帧累积**，按内容去重，每会话上限 300 条 |
| **分析记录** | 每次分析的结论：意图、风险、建议、候选、耗时、所用档案 | 按会话 | 每次分析追加一条 |
| **联系人目录** | 人物身份 `Person`（名字、别名、身份描述） | **全局**，跨会话通用 | 人工维护，冲突时人工值优先 |

两条容易踩的实现约束（iOS 已按此实现，Windows 侧请注意）：

1. **累积层的去重必须按内容指纹（side + sender + text），不能按整条记录比**。
   同一帧读到的所有消息共用同一个时间戳，拿带时间戳的对象直接比会永远不相等，
   重合检测就成了死代码。
2. **记录行的 id 必须是存储的唯一值，不能由「内容 + 时间戳」拼出来**。
   同一个人在**同一屏里连发两条一样的话**会让拼出来的 id 撞车，
   SwiftUI 的 `ForEach` 要求 id 唯一，撞了会渲染错乱。
   累积层仍然按内容指纹去重，两者互不影响。

界面归属：iOS 上是三个 tab（探针 / 记录 / 联系人），记录页按 **群聊 / 单聊** 分两栏，
会话详情里「会话记录」与「分析记录」两块分开。

## 七之二、性能与成本（两端共享实测，**优先级最高**）

### 实测延迟预算

Windows 侧真实调用（见 `docs/win/gate0_findings.md` R3）：

| 环节 | 耗时 | 说明 |
|---|---|---|
| 感知（DeepSeek 视觉） | **4.4 ~ 15.5s** | 波动大，是瓶颈 |
| 判断（Jev 7 题） | 1.0 ~ 1.7s | 很快 |
| 起草（3 条候选） | 2.2 ~ 7.0s | |
| 排序（Jev） | 0.9 ~ 1.1s | 很快 |
| **合计** | **8.7 ~ 16.5s** | |

### 三个反直觉的实测结论（都会影响实现决策）

**1. 关闭思考只省 16%，压缩输出才是真杠杆。**
Windows 侧文档推测"换非思考型视觉模型是最直接的优化"。iOS 侧用**真实 prompt + 整图**实测（同一张桌面截图）：

| 变体 | 延迟 | 推理 token | 输出 token | JSON 有效 |
|---|---|---|---|---|
| 基线（思考开） | 5.0s | 197 | 598 | ✅ |
| `thinking: {"type": "disabled"}` | **4.2s** | 无 | 328 | ✅ |
| `reasoning_effort: "minimal"` | 4.8s | 296 | 664 | ✅ |

关闭思考确实生效（推理 token 归零）且 JSON 仍有效、消息数一致，但**只省 0.8 秒**。
延迟由**输出 JSON 的长度**主导——7 条消息要 598 个输出 token。**建议方向：精简输出**
（去掉 `notes`、缩短 `description`、只返回最近 N 条），而不是换模型。

**2. 裁小图不能降延迟，反而更慢。**
Windows 侧把消息区从 783px 裁到 420px，耗时从 4.79s 涨到 6.41s：输入 token 降了（1347→987），
但**推理 token 涨了**（732→918）。而且裁掉标题会丢会话键、字符误读变多。
**结论：生产路径送完整消息区，不要为了省钱裁图。**

**3. "实时感"的正解是主动触发，不是压模型。**
8~16s 在"用户点了才分析"的交互模型下不可接受；但本项目是**新消息到达就自动分析**——
门判定画面稳定即触发，等用户看向面板时结果已经在了。所以：
- 目标不是把 16s 压到 2s，而是**让这 16s 发生在用户不需要等待的时间里**
- 这要求**两段式渲染**：判断（占总耗时约 1/10）先画出来，候选再补
- 也要求门的静默窗口不能设太长，否则消息到了却迟迟不触发

### 采集侧的两条硬经验（iOS 已照搬）

**1. 静默判定必须由定时器驱动，不能只在帧到达时判定。**
WGC 与 ScreenCaptureKit 都是**只在内容变化时送帧**。所以"最后一帧到达"不等于"已经静默"——
靠帧到达判定的话，内容稳定后不再送帧，稳定帧永远发不出去（Windows 侧踩过，初版一直靠 maxWait 兜底）。
iOS 侧 `FrameGate` 因此拆成两个入口：`ingest()` 只更新"画面变没变"，`tick()`（0.5s 定时器）负责判定与放行。

**2. 输入区的底色可能与消息区完全相同。**
Windows 侧实测微信 4.1.13.65 深色模式：消息区与输入区底色都是 `(30,30,31)`，
唯一区分是 y=815 那条分隔线（整行同色 `(39,39,40)`，占 0.979）。阈值卡到 0.985 就会跳过它、
把窗口底边当成下边界。**别用固定比例裁底**——这是 iOS 侧本地原型踩过的同类坑（84% 固定带删掉了最新消息）。

### 间歇性空返回

感知有约 **1/8 的概率返回空正文**（思考型模型烧完 4000 max_tokens，正文为空）。两端都要：
拿到空正文时**明确报出原因并重试一次**，不要静默失败。iOS/桌面共用的 `providers` 层已实现
（报错信息里会写明"这次 N 个 token 全花在推理上"）。

## 八、需要两端一起定的事

1. **风格分组的排序接口**：每个风格各调一次排序题（成本 ×风格数），还是一次请求带 `style_id` 让模型分组输出？前者贵但稳，后者省但依赖模型遵守分组。
2. **`no_reply` 在候选里的位置**：截图里是第三个折叠组。要不要在"风险 ≥7"时把它**移到最后并默认折叠**（避免用户顺手选"不回"）？
3. **别名归并的确认方式**：自动归并 + 界面标注，还是需要人工点一下确认？后者更准但多一步操作。
4. **身份设置与记忆的冲突提示**：人工改了身份后，是否要主动提示"记忆档案里有一条冲突，要覆盖吗"。
5. **低置信度的阈值**：<50% 降强度、<40% 加提示，这个分界是否合适（基于实测 `best_action` 只有 14~30% 把握度定的）。
6. **群聊受众规模是否影响生成**：214 人群 vs 3 人群，候选措辞应该不同。要不要显式把 `audience_size` 写进起草 prompt。
7. **共享文件的同步方式**：`questions.json` / `prompts.json` / 本文档，Windows 侧是复制还是引用？建议引用同一份，像桌面版现在引用 `tools/ios-spike/` 那样。

## 九、优先级建议

**先做（直接影响准确度与可用性）**
1. **压缩感知输出**（七之二第 1 条）——延迟的最大杠杆，两端都受益
2. **身份设置**（`session_key` 粒度）——它是"关系前提靠猜"这个已定位缺陷的正解
3. **别名归并**——群聊里昵称读错会直接导致发言人张冠李戴
4. **两段式渲染**确认已落地（判断先出、候选后补）
5. 风格分组排序的接口定下来

**后做（体验优化）**
6. 低置信度的显示策略
7. `no_reply` 的位置策略
8. 受众规模进 prompt

**共用基建**
9. `providers.json` / `questions.json` / `prompts.json` / 本文档，两端引用同一份，改动同步
10. 空正文重试策略两端一致
