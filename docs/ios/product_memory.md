# 产品策略：按群组/联系人维护记忆档案，并把对话沉淀为语料

日期：2026-09-21　状态：机制已实现并跑通，群聊题目集尚未校准

## 一、为什么记忆能提高准确度（有实测依据，不是设想）

本轮实测出一个缺陷及其根因：

| 数据 | 跨题矛盾 |
|---|---|
| 标注集 30 条（全是一对一关系场景） | 0 处 / 触发 50 = 0.0% |
| 真实群聊截图 | 出现「要你办事」+「需要行动」+「不必给实质内容」这种自相矛盾的组合 |

根因不是某道题措辞差，而是**关系前提靠猜**：题目集预设了"对方在测试你在不在乎"，
群聊里没有这层关系，于是判断层把不存在的意图读了出来。

记忆档案解决的正是这个：把"这个群是什么、说话的人是谁、我和他什么关系、我答应过他什么"
变成**已知输入**。这是准确度提升的主要来源，也是它和"锦上添花的功能"的区别。

同一轮还发现第二个缺陷：**群聊里所有发言人都被压成一个 `other`**，判断层看到的是
"一个人说了所有话"，于是无法判断"这个问题别人已经回答过了"。已修：state 现在逐条带 `sender`，
另有 `senders` 列表与 `distinct_speakers` 计数。

## 二、记忆的四条硬规矩

违反任何一条，记忆都会从资产变成负债——**一条记错的"事实"比没有记忆更糟**，
它会稳定地把判断带偏，而且没人会发现。

1. **必须带出处**：`evidence` 存消息原文片段，没有出处的不许入库。代码里强制执行：
   蒸馏结果缺 `key`/`kind`/`text`/`evidence` 任一项直接丢弃（`memory.py` 的 `distill`）。
2. **只存可核对的事实，不存推断**：存「群成员甲说'你不用手动拉人'」，
   不存「他很在意拉人效率」。推断留给判断层每轮重算——它自己会算，存下来只会固化错误。
3. **结构化字段而非自由文本摘要**：`kind` / `key` / `about` / `expires` 都可查询、可覆盖、可审计。
   自由文本摘要没法按 key 更新，也没法设过期。
4. **有生命周期**：`commitment` 类必须给 `expires`。否则三个月前的承诺会被当成现在的事实。

## 三、记忆的五类内容与归属

| kind | 内容 | 例子 |
|---|---|---|
| `identity` | 对方是谁、和我的关系、角色 | 「群成员乙是项目群的活跃成员」 |
| `fact` | 关于对方或这个群的稳定事实 | 「群成员甲在负责推广拉人」 |
| `commitment` | 谁答应过做什么（必须带 expires） | 「我答应整理聊完总结发群里」 |
| `preference` | 偏好、习惯、忌讳 | 「群里大家习惯用表情包回应」 |
| `boundary` | 不能碰的话题 | 「别在群里提钱」 |

每条另有 `about` 字段标明**这条关于谁**——这是用户明确要求的：群聊场景必须能区分不同的人。
`source_sender`（谁说的）与 `about`（关于谁）是两个不同维度，不能混。

注入判断层时按人分组（`brief()` 输出 `about_people`），让判断层知道"这句话关于谁"。

## 四、存储与流转

```
感知（截图 → 结构化对话，带 sender）
   ↓
读取该会话的档案 → brief() 注入 state.chat.memory
   ↓
判断（按场景选题目档案：一对一 / 群聊）
   ↓
起草（prompt 里也带发言人，群聊才不会把不同人的话当一个人）
   ↓
（可选）把这次对话蒸馏回档案，key 相同则覆盖更新
```

原型阶段档案落在 `tools/ios-spike/out/memory/`（已被 `.gitignore` 排除，含真实聊天内容）。
真机版应存在设备本地沙盒，不上传——这是隐私底线，与项目"只读你自己有权查看的聊天"一致。

## 五、把对话沉淀为语料（用户提的"可训练的语料"）

### 先说清楚"训练"能做什么、不能做什么

**不能**：微调 Jev。它是 TypeSafe 托管的 System One 模型，没有对外微调接口。
所以"训练"的准确含义是下面三件事，不是 fine-tune：

1. **校准题目措辞**——这是 `calibrate.py` 已经做的（当前一对一 7 题命中率 70%~100%，
   `danger_level` 平均绝对误差 0.490，三项验收门槛都过）。群聊那套需要同样的流程。
2. **少样本示例**——把"我方真实发出去的回复"当作正样本放进起草 prompt，
   让风格贴近本人（现在 prompt 里只有关系描述，没有例子）。
3. **评估排序质量**——用户实际选了哪条 / 实际发了什么，是**唯一的真值信号**，
   可以用来量化"Jev 排第一的那条是不是用户真想要的"。

### 每条分析都天然产出一条标注样本

```
（截图 → 对话 + sender） + （档案快照） + （Jev 七题答案） + （3 条候选） + （用户实际发了什么）
```

最后一项是灵魂：**它是"建议好不好"的唯一客观真值**。安卓版现在不收集这个——用户点了"填入"
之后发了什么，没有任何记录。iOS 版应在填入/复制后回采一次。

### 语料收集的落点

- 扩充 `tools/jev/fixtures/labeled_set.json` 的**群聊部分**（现在 30 条全是一对一）
- 这是修群聊题目集缺陷的**唯一正路**：本轮已定位群聊题目集有一处稳定矛盾
  （`need_reply=false` 却建议 `answer_directly`，置信度仅 41%），但**靠猜改措辞不行**，
  必须先有群聊标注数据。预计 20~30 条群聊对话即可跑第一轮校准。
- 隐私：语料含真实聊天，只存本机、不进入 git（`out/` 已排除），与档案同一处理

### 收集方式（不需要用户额外劳动）

`pipeline.py` 每次分析已经输出结构化 JSON（含对话、答案、候选、排序）。加一个
`--log-corpus` 开关把它们追加到 `out/corpus/`，跑一段时间就自动积累了。
需要用户做的只有两件：选择性地标几条人工答案（真值），以及在填入后回采实际发出的内容。
