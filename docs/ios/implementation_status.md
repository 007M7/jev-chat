## 二、为什么实时活动没生效

`Widget/JevWidgetBundle.swift` 与 `Shared/JevActivityAttributes.swift` 都在仓库里，`Sources/Output/LiveActivityController.swift` 也会尝试启动活动，但 `project.yml` 里 **widget 扩展的 target 被注释掉了**。原因有两条，都是免费签名带来的：

1. 免费账号下 Sideloadly 的"自动 Bundle ID"会给主 App 改名，而扩展的 Bundle ID 必须以上层 App 的 ID 为前缀——两者对不上，iOS 判定包结构不合法，表现为**「不受信任的开发者」且信任条目生不出来**（装不上）。
2. 勾选其它 patch 选项时，Sideloadly 里"去掉扩展"的那段代码会崩（实测 Guru Meditation）。

所以当前策略是构建侧直接不出扩展。**已生效的显示通道是通知横幅**，它承载了候选选择这条主交互；实时活动要等 Bundle ID 方案理清后再加回来（或者用付费账号）。

## 三、关键实测数据

### 耗时（同一批真实截图，多次调用）

| 环节 | 耗时 | 备注 |
|---|---|---|
| 感知 | 4.39 / 4.79 / 5.72 / 5.87 / 5.94 / 6.59 / 7.07 / **15.46** s | 瓶颈，波动大 |
| 判断 | 1.01 / 1.21 / 1.52 / 1.69 s | |
| 起草 | 2.17 / 3.94 / 5.17 / 7.02 s | 快速模式跳过 |
| 排序 | 0.92 / 0.96 / 0.99 / 1.13 s | 快速模式跳过 |
| **合计** | **8.7 / 13.7 / 13.9 / 16.5 s** | |

两个反直觉的结论（都影响实现决策）：

1. **裁小图不能降延迟**。把消息区从 783px 裁到底部 420px，耗时反而从 4.79s 涨到 6.41s：输入 token 从 1347 降到 987，**输出（推理）token 从 732 涨到 918**。耗时由思考型模型的推理长度主导，不是图像大小。而且裁掉标题会丢会话键、字符读错变多。所以**生产路径送完整消息区**。
2. **判断比感知快得多**（1.0~1.7s vs 4.4~15.5s）。所以两段式渲染是对的：危险等级和意图在感知结束后 1 秒内就能出来，候选再慢补。

### 成本闸门

感知一次约 5 秒且要花钱，绝不能每帧都调。实测采集 30–60 fps，所以本地门必须把绝大多数帧挡掉。当前阈值（`FrameGate.Config`）：

| 参数 | 值 | 理由 |
|---|---|---|
| 抽样间隔 | 500ms | 转图是最贵的本地操作 |
| 消息区比例 | 屏高 15%~80% | 避开顶部状态栏与底部输入框 |
| 缩略图 | 48×96 灰度 | 判断"画面变没变"足够，共约 9 KB |
| 单像素灰度阈值 | 12 | 抗渲染噪声 |
| 变化像素占比 | 2% | 低于此视为没变 |
| 静默时长 | 1.5s | 避免把滚动中的中间态送出去 |
| 上限等待 | 6s | 应付会动的表情包（静默永远等不到） |

**门必须由定时器驱动，不能只在帧到达时判定**——ScreenCaptureKit 只在内容变化时送帧，所以"最后一帧到达"不等于"已经静默"；内容稳定后不再送帧，靠帧到达判定的话稳定帧永远发不出去。这条是从桌面实现踩坑后带过来的。

### 归属判定的退化与放弃

早期尝试在本地做「这条消息是谁发的」，用 OCR 文字框的几何位置判断。合成集上的结果：

| 规则 | 准确率 |
|---|---|
| 中心法（照搬 Android 的 `cx > 屏宽/2`） | 96.3%（6 例中 5 例） |
| 边缘法（贴边优先，退回中心） | 96.3% |
| 颜色法（气泡底色：绿=我 / 白=对方） | 100% |

**但这三个数字只在合成集上成立，真实数据上会退化**：颜色法依赖浅色模式与默认气泡配色，深色模式或自定义聊天背景就没了；几何法在**折行长行越过中线**时必然判错——根因是 Android 读的是气泡节点的 bounds，而 OCR 只能拿到**文字行的框**，文字行在气泡里的横向位置是任意的，几何位置不可靠。

结论：**本地几何归属不成立**，改为把整屏交给视觉模型，由模型同时给出文本与发言人。这是从"本地 OCR + 几何规则"切到"VLM 感知"的直接原因。

消息切分上另修掉四个真实 bug（都写成用例覆盖了）：固定百分比顶带误删无时间戳的首条消息、标题宽度门槛读不到两字短名、折行合并被"负间隙"判据拒绝（OCR 相邻行会重叠 4~6px）、底部固定边界带误删最新一条。

| 位置 | 内容 | 上限 |
|---|---|---|

## 四、题目与档案

- 题目、感知 prompt、provider 注册表三份 JSON 是**三端共用**的，构建时从 `tools/jev/` 拷进 App 包（仓库里不放副本）。iOS 侧不重新定义任何默认值。
- 群聊与单聊走**不同题目档案**：`profiles.one_on_one`（已校准）与 `profiles.group`（**未校准**）。单聊档案里的关系描述刻意不预设亲密关系——早期版本预设了"伴侣"，结果在技术群里生成了恋人语气的话术。
- 群聊档案的触发有兜底：感知没给出 `is_group` 时**默认走中性档案**（"该亲密时没亲密"是轻错，"在工作群里凭空造出恋情"是重错）；此外只要**对方阵营出现 ≥2 个不同发言人**就强制判为群聊——这条判据完全来自数据本身，比模型给的字段可靠（实测踩过：256 人的群被判成单聊）。

## 六、跑一遍大概要多久

从零到能用（不含写代码）：

| 步骤 | 耗时 |
|---|---|
| Fork 仓库、跑一次 Actions | 约 5 分钟（预览镜像偶尔要重试） |
| Windows 装 Apple 驱动 + Sideloadly | 20~30 分钟（驱动被打掉时更久） |
| 自签安装 + 信任证书 | 10 分钟 |
| 填密钥、选 provider、跑通一条分析 | 5 分钟 |

之后每 7 天重签一次；AltStore 可以在同一 WiFi 下自动刷新，把这件事降到几乎无感。
