# iOS 感知层验证报告（Gate 0）

日期：2026-09-21　范围：`tools/ios-spike/`　复现命令见文末

## 一、要回答的问题

安卓版靠无障碍节点树拿到「气泡文本 + 屏幕坐标」，iOS 不提供这个能力。iOS 版唯一能把对话变成文本的办法是从截图像素里读。Gate 0 要回答的是：**这条路准不准，以及准到什么程度才敢投入原生 App。**

计划的原始假设是「'谁说的'那套左右位置判定可以沿用」——因为 `ChatAppAdapter.kt:60` 的 `cx > width/2` 本来就是对坐标做纯数学。**这个假设被证伪了**，原因见第四节。

## 二、方法

| 手段 | 用途 | 局限 |
|---|---|---|
| 合成图（`synth.py`，6 例 21 行文字，带 ground truth） | 把 OCR 质量隔离出去，单独量归属规则与折行合并的准确率 | 字体渲染与真实截图不同，文字识别率不可外推 |
| 真实截图 A：`docs/images/overlay.png`（手机版 1200×2670，浅色，含浮层） | 真实像素 + 界面干扰 | 群聊，且"我"发的全是图片 |
| 真实截图 B：用户提供的微信桌面版截图（1376×764，深色，群聊） | 真实桌面布局 + 深色模式 | 群聊，无"我"发的消息 |
| 端到端真实调用 | 验证「截图 → 判断 → 起草 → 排序」整链 | 判断走 TypeSafe 直连；起草因余额问题未跑通 |

归属准确率的量法：逐 OCR 文字块判定，看它落在哪个 ground truth 气泡里，side 对不对。刻意与"消息条数"分开量，避免把两种不同的错混成一个数字。

## 三、结果：归属规则

| 规则 | 归属准确率 | 消息条数正确 |
|---|---|---|
| `center` 中心法（照搬安卓 `cx > 屏宽/2`） | 96.3% | 5/6 |
| `edge` 边缘法（贴边优先，退回中心） | 96.3% | 5/6 |
| `color` 颜色法（气泡底色：绿=我 / 白=对方） | **100%** | **6/6** |

Gate 0 的判据（归属 ≥95%）三条都过，但**这个数字只在合成集上成立**。真实数据上 `color` 规则的适用条件会消失（深色模式、自定义聊天背景、飞书整体左对齐布局）。

几何法唯一失败的是**折行长行越过中线**：左侧气泡里折行的"你还是没当回事"因为文字行中心 x=673 > 屏宽/2=600 被判成"我发的"。根因是**安卓拿的是气泡节点的 bounds，而 OCR 只能拿到文字行的框**——文字行在气泡里的位置是任意的，几何位置不可靠。所以"直接沿用安卓的几何判定"不成立，必须升到气泡级判断（颜色分割就是其中一种）。

## 四、结果：消息切分（修掉四个 bug）

初版在 6 个合成用例上**条数全错**（1/6 正确）。逐个定位后修掉四个，最终颜色法 6/6：

1. **固定百分比顶带误删首条消息**。写死"屏高 14% 以上是标题栏"，没有时间戳的会话首条消息正好落在里面被删（合成用例 c06：10 个 OCR 块只保留 3 个，4 条消息剩 2 条）。安卓版实际用的是 `min(首个气泡 top, 14%)`（`ChatAppAdapter.kt:68`），只移植了 14% 那一半就退化成 bug。
2. **标题识别的宽度门槛**。原先要求标题宽度占屏宽 10%，两个字的名字（"妈妈"）识别不到标题 → 退回固定顶带 → 首条消息又被删（合成用例 c04）。
3. **折行合并被"负间隙"拒绝**。OCR 相邻两行的文字框会互相重叠几个像素（字体框比行距高，实测重叠 4~6px），而合并判据写死了 `gap < -2 即拒绝`，于是折行永远合不上（c02/c05）。改成只拒绝明显往回跳。
4. **底部固定 84% 边界带误删最新消息**。这条在真实截图上暴露：桌面版截图里 Jev 要判断的那条「这个能有落地的伙伴嘛」整条被删。改为**检测到输入栏文字（"发送"等）才裁底**——手机版有输入栏所以照旧裁，"没截到输入框"的图就不再裁。

修完后合成集：归属 96.3%/96.3%/**100%**，条数一致 5/6、5/6、**6/6**。

## 五、结果：本地感知在真实截图上的失败（这是关键）

### 截图 A（手机版，含浮层）

抽出 7 条"消息"，**其中 5 条是截图里 Jev 面板自己的文字**："危险 1/9 安全"、"候选回复（Jev 排序）"、"#1 89% 马上发你,稍等哈 复制 填入"……面板是白色的，颜色规则把它们全判成"对方"。

这条最要命的地方不是识别错，而是**这些内容会被当成对方说的话送给 Jev**，直接污染判断。另外：

- **"（一条普通文字消息）"识别完全正确（置信度 0.98），却被底部边界带当成输入框删掉了**——真实消息丢失
- 被半透明面板遮挡的"安卓可没那么好开发"**OCR 压根没读出来**（对比度不足）
- URL 里的 `/` 被读成 `l`：`blog.caowo.de/posts` → `blog.caowo.delposts`

### 截图 B（桌面版，深色，用户提供）

抽出的 10 条里 **4 条是发言人的昵称**（"成员A"、"误读1"、"误读2"、"成员B"），另有 3 条把昵称和正文粘成了一条（"群成员甲（blake多挂几个二维码"）。文字识别错误包括："突然"→"实然"、"火"→"炊"、"二维码"→" 维码"、"群成员乙"→"误读1"/"误读2"。emoji 丢失（"😴我想睡觉啊" → "我想睡觉呵"），而 emoji 恰恰是语气信息。

深色模式下颜色规则**完全失效**（没有微信绿/白气泡可言），自动退回几何法；而这又是群聊，所有消息都左对齐，几何法没有任何可用信号——**"谁说的"只能靠昵称，也就是那 4 条被当成消息的东西**。

## 六、结果：端到端真实调用

用截图 B + 本地感知，真实调通判断与排序（`--candidates` 固定候选）：

```
model jev-1.13.0   耗时 1.02s   token 2660/278
  literal_question   是（0.57）
  true_intent        request_action（把握 89%）
  danger_level       1.3/9  Mild tease or a small reminder that is easy
  should_reply_now   否（0.22）
  best_action        acknowledge（把握 19%）
  she_needs          action（把握 96%）
  tension_resolved   否（0.42）

Jev 排序
  #1 · 68.0%  我建个接龙吧，想一起做的先扣1，我统一拉群
  #2 · 30.0%  有的，正在对接几个愿意一起落地的伙伴
  #3 ·  2.0%  嗯，慢慢来
```

结论：**大脑层与平台无关，这部分成立**。判断、起草 prompt、排序题原样可用，排序结果合理。

但暴露两个问题：

1. **题目之间仍然互相矛盾**（`CLAUDE.md` 和 `tools/jev/TASK.md` 早就警告过这一条）：`should_reply_now` 给"否（0.22）"，而 `she_needs` 给"要行动（96%）"、`true_intent` 给"要你办事（89%）"。既然对方要的是具体行动，就不该说"不必给出实质内容"。
2. **`best_action` 把握度只有 14%~19%**，两次运行还在 `explain` / `acknowledge` 之间跳。这个题对"群聊里问能不能找到落地伙伴"这类场景的选项集不贴合。

这两个都需要靠标注集重新校准（`tools/jev/calibrate.py`），属于已知待办而非新问题。

## 六之二、结果：视觉模型感知（已实测，取代本地启发式）

用 DeepSeek 视觉（`deepseek-flash`，走用户已有的 key，不需要 OpenRouter）跑同一批截图。

**桌面深色群聊截图（用户提供）：**

| 指标 | 本地 OCR | DeepSeek 视觉 |
|---|---|---|
| 识别出的消息 | 10 条（其中 4 条是昵称） | **7 条，与人工核对一致** |
| 文字准确度 | "突然"→"实然"、"火"→"炊"、"二维码"→" 维码" | 全部正确 |
| "1" 这条消息 | 完全丢失 | 正确识别 |
| 😴 emoji | 丢失 | 读出并说明含义（"带🤗我想睡觉啊文字的贴纸"） |
| 发言人昵称 | 当成消息，还与正文粘连 | 正确忽略并用作 sender 标签 |

**手机版截图（`docs/images/overlay.png`，含 Jev 浮层面板）：**

| 指标 | 本地 OCR | DeepSeek 视觉 |
|---|---|---|
| 面板界面文字 | 抽成 5 条"消息"混进对话 | 按指令忽略，并说明"Jev 分析面板是浮层，已按要求忽略" |
| 猫图/吉娃娃图 | 读不到（返回空） | 描述为"一张黑色小狗的照片"、"两只吉娃娃的合照" |
| 谁说的 | 全部判成"对方" | 绿色气泡正确判为"我" |
| "（一条普通文字消息）" | 识别正确却被边界带删掉 | 正确保留 |
| 输入框草稿 | 正确排除 | 正确排除 |
| URL | `blog.caowo.delposts`（/ 读成 l） | `blog.caowo.de/posts` |
| 被浮层遮挡的内容 | 静默丢失 | 明说"被遮挡无法确认"，不编造 |

**完整链路实测**（视觉感知 → Jev 判断 → DeepSeek 起草 → Jev 排序，全部真实调用，总耗时约 11 秒）：

```
感知  deepseek-flash       1233 in / 598 out    4.5s
判断  jev-1.13.0           2579 in / 276 out    0.98s
  literal_question   是（0.60）     true_intent    request_action（85%）
  danger_level       1.0/9          should_reply_now 否（0.34）
  best_action        make_plan（30%） she_needs     action（90%）
  tension_resolved   是（0.75）
起草  deepseek-flash        222 in / 707 out    4.59s
排序  jev-1.13.0                                0.93s
  #1 · 69%  我这就多创几个码推到项目下，不手动拉，你先睡。
  #2 · 26%  落地伙伴会有的，先按你说的多挂码，我来筛人。
  #3 ·  5%  辛苦你了，是我没安排好，先睡吧，我来盯。
```

起草的候选引用了对话里的真实细节（"多挂码"、"不手动拉"、"先多创几个推到项目下"），说明送进模型的内容是干净的——对比第三节里本地感知那次，候选是凭空生成的通用话术。

**结论：感知层交给视觉模型，本地 OCR 退为离线兜底，这一条现在有实测支撑。**

### 一个必须记住的坑

DeepSeek 这两个模型是**思考型**：`max_tokens` 给少了，推理 token 会吃光额度、正文返回空。实测 `deepseek-v4-pro` 在 `max_tokens=200` 下返回空字符串且 reasoning_tokens=200。所以 `providers.json` 里给它们配了 `max_tokens: 4000`，`providers.py` 也会在拿到空正文时明确报出这个原因而不是静默失败。

## 七、更好的方式：三层感知（既不"纯截图 OCR"，也不"每帧都调大模型"）

你问"是否有更好的方式"——有，但不是换掉截图，而是**别把截图当成一次性 OCR**，也别每一步都求助于大模型。推荐这样分层：

**Tier 0 · 采集：连续流，不是"截图"**
ScreenCaptureKit 给的是持续的视频帧流。本地做像素变化检测，**只在底部消息区真的变了**才往下走。没变就什么都不做，零成本。

**Tier 1 · 本地：iOS Vision OCR + 气泡颜色归属（离线、免费、私密、无网络延迟）**
处理纯文字聊天，这是绝大多数情况。这条路不是想当然——兄弟项目 `jev-chat-JARVIS-windows` 已经用「WGC 截自己的窗口 + 像素锚点定位消息区 + RapidOCR + 按气泡颜色分说话人」跑通，而它明确记录 WeChat 4.x 的 UIA 树只有 2 个节点（走不通）、也拒绝读数据库。**它和我在合成集上量到的"颜色法 100% vs 几何法 96.3%"互相印证。**

但要清醒：**iOS 比 Windows 版难**，这正是本报告第五节那些失败的原因——

- Windows 版能只截自己的微信窗口，iOS 全屏采集会把键盘、通知横幅、灵动岛一起收进来
- Windows 版可以假定固定窗口布局做像素锚点，iOS 要面对主题、字号、深色模式、各种机型
- 群聊（本报告两张截图都是）在本地规则下几乎没有可用信号

所以 Tier 1 不能单独兜住，必须有 Tier 2。

**Tier 2 · 云端视觉模型：只在需要时调**
触发条件二选一：Tier 1 的置信度低，或内容非文本（表情包/图片/语音/引用卡片/红包）。第六之二节的实测数字说明它值得这一次调用——本地 OCR 看不见的东西它都能处理，而且会诚实报告"被遮挡无法确认"而不是编造。
**成本控制靠 Tier 0 的变化检测**，一次对话只有几次请求，不是每帧。

**Tier 3 · 人工精确模式（可选）**
分享/复制文本进来，零 OCR 误差。当 Tier 1+2 都不确定时给用户一个兜底。

### 两个被否掉的方案（说明为什么不做）

- **读微信本地数据库**：Windows 版微信的 SQLite 是可解密的，这是"最可靠的非截图路径"，但它直接违反 `CLAUDE.md` 硬约束第 1 条（不读数据库），兄弟项目也明确拒绝。**不作为选项。**
- **自定义键盘扩展**：只能看到输入框附近的内容（`documentContextBeforeInput`），看不到对方发的消息。**能力上不成立。**

### 一个能让 Tier 1 越用越准的办法

用 Tier 2 当 Tier 1 的**校准器**：抽样跑视觉模型，把它的输出当作 ground truth，回头去调 Tier 1 的阈值、锚点和颜色判据。这样本地规则的准确率会被持续修正，而不是靠人工拍脑袋定一次。这也顺便回答了"本地 OCR 精度不够"这个顾虑——**它够不够用可以测，而且能持续改进。**

## 八、对方案的影响

1. **感知层改走多模态视觉模型**，本地 OCR 退为离线兜底。视觉模型天然解决本地启发式的四类问题：表情包/图片能描述（截图 A 里"我"发的全是猫图，本地 OCR 返回空）、昵称能当发言人标签而不是消息、"谁说的"按语义判断而不是像素假设、界面上的浮层文字能按指令忽略。
2. **成本由本地像素变化检测控制**：不是每帧都调模型，只在"屏幕变了"时才发一次。一次对话实际只有几次请求。
3. **原计划里"沿用安卓几何判定"的说法作废**，改为"气泡级/语义级判断"。
4. 题目集已收口为单一来源 `tools/jev/questions.json`（三端一致性由 `check_questions.py` 校验，52 项，当前有 3 处 em dash/连字符差异），iOS/Swift 侧以后照这个文件实现即可，不会再出现三份手工同步。
5. provider 不再硬编码：端点、模型、密钥环境变量名都在 `tools/jev/providers.json`，判断/起草/感知三个角色各自可指向不同 provider。

## 九、尚未验证（诚实清单）

| 缺口 | 为什么没验 | 怎么补 |
|---|---|---|
| iOS Vision 在真机截图上的中文精度 | 需要真机 + 快捷指令，只能在用户手机上跑 | 用「截图 → 从图像中提取文字」快捷指令，跑 5 类真实截图 |
| 一对一（浅色、有来有回）真实截图 | 手上两张都是群聊，缺"我发的**文字**消息"这一最基本场景 | 用户提供 3~5 张一对一截图后重跑 |
| 深度思考模型的成本明细 | DeepSeek 未提供可查的单价，只能记 token 数 | 按 token 自己算；单次分析约 4000 token 量级 |
| 音频/视频/引用/红包卡片的处理 | 无对应截图 | 后续补样例 |
| 深色模式的**本地**归属判定 | 本地规则在深色下无颜色线索 | 已由视觉模型覆盖，本地不修 |
| 视觉模型感知的稳定性 | 只跑了 2 张截图各 1 次，未做重复性测试 | 同一张图跑 5 次看输出是否一致 |

已由本次验证解决的缺口（原列表中的"视觉模型感知的真实表现"与"起草候选的真实质量"）：见第六之二节。

## 十、复现命令

```bash
cd tools/ios-spike

# 合成集：生成 + 量准确率
python synth.py --out out/synth
python selftest.py --synth out/synth --json out/selftest.json

# 真实截图：本地感知（三种规则对比）
python extract.py --image ../../docs/images/overlay.png --rule color --debug out/real_color.png
python extract.py --image out/real_desktop_dark.png --rule edge --debug out/dbg_desktop.png

# 端到端（需要密钥，只从环境变量读）
export JEV_API_KEY=...
python pipeline.py --image out/real_desktop_dark.png --perceiver local \
  --relationship "这是我们的项目交流群，对方是群友" \
  --candidates "候选1|候选2|候选3"

# 题目集三端一致性
cd ../jev && python check_questions.py
```

`out/` 含真实聊天截图，已在 `.gitignore` 里排除。
